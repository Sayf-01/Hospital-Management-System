# Schema changes: Phase 1 → schema v2

**Status:** DA-1 draft for review by Sayf and Youssef.
**File:** [`sql/schema_v2.sql`](../../sql/schema_v2.sql), built on the Phase 1 schema. The Phase 1 rules are all kept: the composite foreign key `(admission_id, patient_id)`, the unique index for one Primary diagnosis per admission, and the status and discharge checks.

| # | Change | Integration problem it solves | How it solves it |
|---|---|---|---|
| 1 | New table `source_systems` (`source_code` `CHAR(1)` primary key, `CHECK` in `A`–`D`; `hospital_name`, `continent`, `file_format`, `time_zone`) | The integrated database mixes four hospitals, and nothing in Phase 1 said which hospital a row came from or how its times were recorded. | One row per source, stored once. Every source-tagged row points to it through a foreign key, so a row can only claim a source that exists, and its original time zone can be looked up. |
| 2 | `source_code` and `source_local_id` columns, `NOT NULL`, with `UNIQUE (source_code, source_local_id)`, on every data table except `patients` and `icd9_dictionary` | Each source numbers its records from 1, so local IDs clash: admission 1 exists in A, B, C and D. | The primary key is now a new global ID, and the source's own ID is kept beside it. The pair `(source, local ID)` must be unique, so the same source record cannot be loaded twice, while the same local number from different hospitals is allowed. |
| 3 | `source_local_id` is `VARCHAR(50)`, not `INT` | Source IDs are not guaranteed to be numbers in every format, and quarantined rows may hold unreadable IDs. | Text holds any ID exactly as the source sent it, so nothing is lost or reformatted when tracing a row back. |
| 4 | New table `patient_source_map` (`source_code`, `source_local_id`, `patient_id`, `match_rule`, `source_insurance_number`; primary key `(source_code, source_local_id)`) instead of source columns on `patients` | The same person can appear in two hospitals. A single `source_code` column on `patients` could only name one of them. | One integrated patient can have several source records (an M1 merge), and each source record belongs to exactly one integrated patient. `match_rule` records why (`NEW` = not merged, `M1` = merged), and `source_insurance_number` keeps each source's number as received. |
| 5 | New table `patient_match_candidates` (`patient_id_1`, `patient_id_2`, `match_rule`, `reason`, `decision` default `'Not merged'`; `CHECK (patient_id_1 < patient_id_2)`, unique pair) | Some pairs look like the same person but cannot be proven to be (for example, the insurance number is missing on one side). Merging them risks joining two different people's records; dropping the evidence loses it. | Uncertain pairs stay as two separate patients, and the pair is recorded with the rule and reason. The check and unique pair store each pair once. |
| 6 | New table `quarantine_records` (`stage`, `source_code`, `entity`, `source_local_id`, `source_line`, `reason`, `raw_record`) | Rejected records were only in CSV logs, so they could not be counted or shown with SQL, and the report must account for every source row. | Every rejected record is stored with its stage (`load`, `clean`, `relationships`, `chronology` or `integrate`), source, position and reason. `source_line` is text because A and B give a line number but C and D give a position in the XML or JSON tree (for example `$[29].admissions[1].diagnoses[0]`). It is a separate table, so the main tables never hold raw text records. |
| 7 | Every `TIMESTAMP` column is now `TIMESTAMPTZ`; `date_of_birth` stays `DATE` | The sources use four time zones (Toronto, Berlin, Tokyo, Sydney). A plain timestamp cannot tell 08:00 in Tokyo from 08:00 in Toronto. | All times are stored as exact moments in UTC, so events from different hospitals compare correctly. A date of birth is a calendar date, not a moment, so it keeps no time zone. |
| 8 | The database's time zone is set to UTC at the top of the schema (`ALTER DATABASE ... SET timezone TO 'UTC'`) | With `TIMESTAMPTZ`, casting to a date (as Q20 does) uses the client's time zone. pgAdmin on a Montreal laptop would shift some events to a different day than psql on a server. | Every session on this database defaults to UTC, so every client sees the same dates. This also matches the cleaning rule that calendar-day comparisons use the UTC date. |
| 9 | `icd9_dictionary` stays one shared table, with no source columns | Each source sends its own copy of the dictionary. Four copies would make the same code appear four times. | All sources use the same real ICD-9 codes, so the four dictionaries combine into one set, keyed by the code. |
| 10 | `patients.health_insurance_number` keeps `UNIQUE` | Two hospitals could issue the same number to different people. | Krish's generator already writes each source's numbers with a source prefix (`P2-A-…`, `P2-B-…`), and cleaning keeps them as they are, so ordinary numbers cannot collide. A number shared across sources is merged (M1) or handled by rule U2 in the integration rules, so the constraint still holds. |
| 11 | The `radiology_exam_details` view also shows `source_code` | Radiology queries could not show which hospital an exam came from. | The column is passed through from `radiology_examinations`, so traceability works in the view as well. |

Constraints and triggers that check rules across tables (DA-4) will be added to this table when they are written.
